This application idea presents a viable solution for my FM27 desktop career, with fmsave serving as a credible ingestion engine. I intend to develop it as a dedicated Windows CustomTkinter utility, commencing with sequential results and a fixture grid, subsequently incorporating league analysis and formatted exports.

The primary qualification concerns data coverage; the ability to successfully open a save file does not guarantee that every historical fixture, score, or match statistic can be recovered. It is essential for the application to transparently represent this coverage, ensuring that its tables and charts maintain their integrity and trustworthiness.

I have reviewed the current fmsave documentation and conducted an independent assessment of my draft. Additionally, I replicated the fixture grid failure using its demonstration data.

While the integration with fmsave is functional, it does have specific limitations.

The documentation presently refers to fmsave version 0.12.4, which was released on 13 November 2026. The proposed methods fmsave.open(...), career.fixtures(), and .to_pandas() are confirmed APIs. The maintainer characterises the library as an offline, read-only save parser that does not interact with the memory of the running game. The release notes include an overview of fmsave and the Table API.

The pivot issue has been confirmed through execution. The sample generates 30 rows but only three distinct home/away pairings, resulting in the error: ValueError: Index contains duplicate entries, cannot reshape. Its axis logic would also exclude Aston Villa, Liverpool, and Manchester United. Replacing pivot() with pivot_table(..., aggfunc="first") would conceal additional matches, rendering it an unsuitable solution.

I propose that the initial version be organised around a concise, explicit data contract.

It is crucial to retain the original fmsave fields at the import boundary, and to derive display values separately. Key fixture fields include:
- Competition and stage: competition_id, stage_id, season_start_year.
- Scheduling: date, kick_off_time, round, round_index.
- Identity: home_team_id, away_team_id, with club names as display labels.
- Results: played, nullable home_goals, and away_goals.

These fields are documented and differ from the draft’s invented application columns, such as Season, HomeTeam, and ScoreStr, necessitating a deliberate mapping layer. The round_index is zero-based and may be absent; the season_start_year can also be missing. The documented fixture record does not provide a universal fixture UID, thus requiring a collision and rescheduling policy for importing successive saves.

In addition to the fixtures, it is essential to retain import metadata, including the source save, game build, parser version, import time, reader warnings, and counts of missing results. Optional match statistics should be maintained as a separate dataset linked to fixtures, with ambiguous joins either rejected or reported.

This structure delineates clear behaviours for each requested feature:
1. **Weekly Sequential Results**: Default to chronological order and group by an explicit week-start date. Offer competition matchday grouping as a separate option. A delayed match should appear on its recorded date while retaining its original round label.
2. **Fixture Grid**: Use home teams as rows and away teams as columns, keyed by team IDs. Each cell should accommodate more than one meeting, displaying multiple scorelines or providing a fixture list. Indicate a date for unplayed fixtures and "result unavailable" for played fixtures without a decoded score.
3. **Form and Running Totals**: Calculate Wins/Draws/Losses, goals for, goals against, goal difference, and points from usable results. Clearly state the points system. If relevant results are missing, mark the affected totals as incomplete.
4. **League-Position History**: This feature demands a more rigorous approach. Reproducing the game’s table necessitates applicable points rules, tie breakers, deductions, stage boundaries, and sufficient historical data. An initial implementation can present calculated standings under specified rules; aligning with the official table will be a separate validation step.
5. **xG Analysis**: Display this only for matches with available statistics, including a coverage count such as "18 of 30 played matches have xG". Missing values must remain unaddressed.

The threaded design should encompass the entire data pipeline.

The proposed separation between FMDataManager, the application controller, and the views is logical and allows for the application to remain compact while initially contained within a single module.

The worker process should independently open its own fmsave Save, load the necessary tables, validate and transform them, and then return a complete result via a queue. The main thread should poll this queue using after(), install the new dataset, and update the CTk widgets. The maintainer explicitly states that a Save is not thread-safe, though returned tables and records can be shared following its closure.

Two critical details require attention:
- A failed second import should retain the previous valid dataset. Avoid gradual mutation of the shared manager while the worker is still loading.
- Filtering, analysis, and export operations can also be resource-intensive. Shift substantial computations to worker threads, creating widgets on the UI thread in batches where necessary.

A grid accommodating 20 teams necessitates practical horizontal navigation; at the draft’s 90 pixels per cell, the data columns alone encompass approximately 1,800 pixels. Responsiveness and grid usability should be assessed during the actual implementation, as the current draft does not guarantee a frame rate of 60 FPS.

The recommended development sequence is as follows:
1. Validate one copy of my FM27 save. Establish its exact build, recover a selected competition and season, count played fixtures with usable scores, and compare a sample of dates, opponents, and results against the game. Execute the library’s validation report and review its warnings; passing reader checks alone does not confirm the accuracy of every value.
2. Construct the core desktop views. Incorporate competition/season selection, chronological results, the grid, and a team filter. Include visible coverage information from the outset.
3. Integrate analysis and exports. Implement calculations for form, cumulative points, and goals, followed by filtered CSV, formatted Excel, HTML, and Markdown outputs. Exports should include the selected competition, season, and any pertinent coverage limitations.
4. Introduce historical comparisons. Implement position charts, comparisons across seasons, and imports from successive saves once fixture identity and competition rules are established. Retaining earlier imports would facilitate the preservation of results that subsequent saves may no longer expose.

Initial validation cases should encompass repeated meetings, an away-only team, a delayed fixture, a played match without a decoded score, a competition with no played matches, and a failed import following a successful one. These scenarios directly target the weaknesses identified in the draft.

I recommend we proceed with a CustomTkinter prototype after resolving the Python version conflict and validating one authentic save. The library APIs support the intended direction; however, compatibility and result coverage for my specific FM27 career remain unverified.
